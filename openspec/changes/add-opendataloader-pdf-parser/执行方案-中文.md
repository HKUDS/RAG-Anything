# OpenDataLoader PDF 接入完整执行方案

## 1. 结论与目标

本次变更将 OpenDataLoader PDF `2.5.0` 作为 RAG-Anything 的**可选 PDF 解析后端**接入，用于受控评估其在中文文档、表格、多栏版面和可追溯来源方面的实际表现。

它不是 Docling、MinerU、Marker 或 PaddleOCR 的替代品，也不会修改现有默认解析器、非 PDF 路由、历史知识库或前端上传流程。最终是否扩大使用范围，完全以内部测试、资源数据和许可证审查结果决定。

## 2. 范围与硬性边界

### 本期包含

- 新增 `opendataloader` 解析器实现，仅处理 PDF。
- 新增可空配置 `PDF_PARSER=opendataloader`；只有 PDF 使用它。
- 接入本地 fast mode，输出 JSON、诊断 Markdown、图片及结构化 provenance sidecar。
- 将标题、段落、列表、表格、图片、公式映射为既有 `content_list`。
- 强制验证 Java、产物 schema、媒体路径、完整页覆盖、缓存身份和安全扫描。
- 提供可选 Python extra、可选 JRE 17 镜像构建路径、测试、SBOM、许可证门禁、隔离灰度和回滚流程。

### 本期明确不做

- 不替换现有 `PARSER` 默认值，不改动 DOCX、图片、音视频或 Office 处理。
- 不启用 hybrid、GPU、模型下载、远程解析、自动 fallback、自动多后端路由。
- 不增加上传级 parser 选择 UI/API，不做 bbox 高亮引用 UI，不重解析历史知识库。
- 不把“上游基准第一”视为本系统结论；只以内部语料的实测结果决策。

## 3. 目标架构

```text
上传任务 -> 现有鉴权/去重/队列 -> process_worker
                                      |
                                      +-- 非 PDF：沿用 PARSER 与既有路由
                                      |
                                      +-- PDF 且 PDF_PARSER=opendataloader
                                             |
                                             +-- OpenDataLoaderParser
                                                   |
                                                   +-- 本地 Java/JAR fast mode
                                                   +-- JSON 规范化
                                                   +-- 页覆盖、路径、schema 校验
                                                   +-- content_list + provenance sidecar
                                                          |
                                                          +-- 既有注入扫描/入库/任务状态
```

关键原则：JSON 是唯一入库数据源；Markdown 仅用于诊断，绝不能再次入库造成重复文本。JVM 只在现有后台 worker 中启动，绝不能在 FastAPI 请求线程中运行。

## 4. 配置、依赖与部署设计

1. 新增 `pdf_parser` 配置及环境变量 `PDF_PARSER`。未设置时行为必须与当前版本完全一致；设置为 `opendataloader` 时仅 `.pdf` 使用新后端。
2. 新增 `opendataloader` optional extra，固定 `opendataloader-pdf==2.5.0`，同步修改 `pyproject.toml`、`setup.py` 与 `uv.lock`；不得加入默认 `requirements.txt`。
3. Docker 提供 opt-in 构建路径，安装 `openjdk-17-jre-headless` 和 optional extra；默认镜像不增加 Java 或 SDK。
4. 增加非敏感配置：输入字节上限、页数上限、JVM 堆/线程上限、单文档超时、并发、输出保留期限。
5. `check_installation()` 独立校验 Python 包、Java 可执行文件和最低版本，错误必须说明缺失项且不得联网。
6. 不允许 `hybrid`、`hybrid_url`、`content_safety_off` 或任何远程服务参数；上游安全过滤保持开启。

## 5. 首先执行的阻断验证

在写正式适配器前，必须针对固定的 `2.5.0` 版本执行合同验证（contract spike），确认：

- JSON、Markdown、图片产物的准确文件名和 schema；
- 标题、表格、图片、公式和 bbox 的实际字段与坐标系；
- 能否可靠表达每一页的成功/失败状态，尤其是空白页；
- 页分隔符、损坏 PDF、加密 PDF、异常返回的真实行为；
- SDK/JAR 是否会进行网络、模型或 hybrid 服务访问。

成功退出的 Java 进程不代表所有页面成功。若批量产物无法证明每一页（含空白页）完整处理，则必须实现经过验证的逐页策略；无法证明时，变更不得进入生产或灰度阶段。

## 6. 解析器实现与数据契约

### 6.1 新模块与注册

创建 `raganything/parser/opendataloader_parser.py`，实现 `OpenDataLoaderParser(Parser)`。在 `raganything/parser/__init__.py` 中确定性注册，使每个新 worker 都能发现它；模块导入本身不得依赖 Java 或 optional extra。

### 6.2 调用和资源控制

- 只通过官方 `opendataloader_pdf.convert()` 调用本地 fast mode。
- 输入路径必须 resolve；输出路径通过现有唯一目录策略产生。
- 使用 worker watchdog、解析器超时、文件/页数预检、JVM 堆和线程限制、并发限制。
- 超时要终止整个转换进程树，覆盖 Windows 与容器场景。
- 输入超出硬上限：非重试校验失败；运行超时或暂态资源失败：可重试 parser-stage 失败。
- 禁止静默切换到 Docling/MinerU，避免两个后端的部分结果混入同一文档。

### 6.3 元素映射

| 上游元素 | 系统输出 | 规则 |
|---|---|---|
| heading/paragraph/list/caption | `text` | 页码转为零基 `page_idx`；标题层级写入 `text_level` |
| table | `table` | 生成规范化 `table_body`/兼容表格数据和 caption |
| image | `image` | 仅接受文档输出根目录内的安全绝对 `img_path`，并调用既有公共媒体 URL 映射 |
| formula | `equation` 或 `text` | 既有公式契约可表达时用 equation，否则安全退化为文本 |
| 未知类型 | `text` 或失败 | 必须记录 provenance；不能静默丢弃 |

图片引用必须防止路径穿越、符号链接逃逸和缺失文件；不安全引用只能变成被记录的安全文本占位，不能读取任意本地文件。

### 6.4 Provenance 与状态数据

每个元素保留上游 ID、源页码、语义类型、标题层级和标准 bbox：`[left,bottom,right,top]`，单位为 PDF point、原点为左下角，并记录页坐标基准。

在文档专属输出目录原子写入 sidecar manifest，保存原始 JSON 身份、规范化块身份、覆盖清单和元素 provenance。`doc_status.metadata` 只保存轻量信息：有效 parser、版本、fast mode、schema 版本、页覆盖和相对 sidecar 路径；不能把原始 JSON、全文 bbox 或任意本地绝对路径塞进状态记录。

sidecar 必须纳入重试覆盖、文档删除、知识库删除和输出保留期的生命周期处理。

## 7. 页覆盖、缓存与入库门禁

1. 将当前仅针对 Docling 的页覆盖检查泛化为解析器能力契约。
2. Docling 与 OpenDataLoader 都必须返回：`source_total_pages`、`successful_pages`、`failed_pages`、`skipped_pages`，且四类状态完整、互斥、无遗漏。
3. 源页数由本地 `pypdf` 读取；没有可证明的上游页状态时，不能把进程退出码当作成功。
4. 存在失败、跳过、漏页、重页、空白页未证明或状态重叠时，必须在质量检查、缓存、`doc_status` 成功和 LightRAG 入库之前失败，错误码为 `pdf_page_coverage_incomplete`。
5. 缓存键和缓存元数据增加有效 parser、包版本、固定 fast mode、适配器 schema 版本及影响语义的选项。版本或模式变化必须缓存失效；相同且已验证的身份才允许命中。

## 8. 安全、合规与可观测性

### 安全

- 所有文本仍经过现有文档注入扫描、RBAC、上传校验、文件锁、审计和后台任务清理。
- 不记录文档正文、凭据或不应暴露的绝对路径。
- 校验 schema、路径、媒体、页覆盖后才允许任何持久化；失败时 fail closed。

### 可观测性

记录结构化指标和日志：解析器、包版本、源页数、输出块数、耗时、结果类别，以及 Java/前置检查、限制、转换、schema、页覆盖和映射失败类别。

### 补充的强制安全验收

- 对 JSON 总大小、元素数、媒体数量、媒体总大小和单文件大小设硬上限；超限、失败或取消时清理该文档专属输出目录。
- 严格校验 JSON：拒绝重复键、不兼容 schema、越界页码、重复元素 ID、非有限数值，以及反向或超出页面边界的 bbox。
- 缓存命中时重新验证覆盖 manifest、sidecar 存在性和内容 hash；任一不符即废弃缓存并重新解析，不能只依赖 cache key。
- 输出目录和 sidecar 采用最小权限与防 TOCTOU 的安全读取；测试“校验后替换为符号链接”的攻击路径。
- worker 解析期间禁止外网访问和模型下载；任何网络尝试必须失败闭合，遥测只记录类别。
- `pypdf` 无法读取页数（包括加密或损坏 PDF）时，必须在转换前作为不可重试校验错误失败，且不得产生缓存或 chunk。

### 许可证与供应链门禁

OpenDataLoader 核心许可证不能等同于整个分发物的许可证。发行 wheel、JAR、离线包或容器前，必须：

- 对最终 wheel、fat JAR、OS、Python、Maven、npm 和容器生成 CycloneDX 或 SPDX SBOM；
- 固定并保留 `LICENSE`、`NOTICE`、第三方 notices、组件许可证文本和不可变的对应源码引用；
- 对账实际依赖与上游清单，重点核对 veraPDF POM `1.31.x` 与 notices `1.29.x` 的不一致；
- 出现 `NOASSERTION`、未知许可证、缺失 notices 或版本未对账时阻断分发；
- 明确该审查只覆盖此次新增集成，不代表项目所有既有依赖已经完成清关。

## 9. 文件级实施清单

### 阶段 A：基础与合同验证

1. 固定版本、wheel/JAR hash、源代码 revision 与许可证证据。
2. 添加 optional extra、锁文件和 opt-in Docker JRE 17 构建。
3. 编写 `PDF_PARSER` 与资源参数文档，不修改用户 `.env`。
4. 完成 contract spike，并决定批量页证明或逐页验证策略。

### 阶段 B：适配器

1. 实现安装检查、PDF-only 边界、fast mode 调用和受控输出目录。
2. 实现 JSON 发现、schema 校验、页码转换、元素映射、媒体 containment 和安全降级。
3. 实现 sidecar、bbox 标准化、页覆盖清单、错误分类和资源控制。

### 阶段 C：系统集成

1. 注册解析器并保持 optional import 懒加载。
2. 在 `raganything/config.py`、初始化代码、`process_worker.py` 和知识库 worker 配置中传递 `pdf_parser`。
3. 在 `DocProcessorMixin` 按扩展名选择有效 parser；非 PDF 完全走旧路径。
4. 泛化页覆盖门禁，升级缓存身份与 `doc_status.metadata`。
5. 接入任务状态、重试、锁、watchdog、进程树清理、结构化日志和指标。

### 阶段 D：自动化测试

1. 单元测试：安装检查、JSON 映射、顺序、标题层级、表格、图片、公式、bbox、sidecar、缓存身份。
2. 负向测试：缺包/缺 Java/旧 Java、超限、超时、损坏 JSON、未知类型、媒体逃逸、空白页、重复页、缺页、清理失败。
3. 契约测试：`PDF_PARSER` 只影响 PDF；DOCX/图片仍使用全局 parser；Docling 覆盖逻辑不回归。
4. worker 新进程测试：配置传递、失败码、无部分 chunk、重试、后台任务 drain。
5. 安全测试：所有新文本仍触发注入防护；日志和 sidecar 不泄露正文、密钥或危险路径。
6. opt-in 真栈测试：Java、optional extra、真实本地 PDF 与空白页 fixture；不得联网或下载模型。
7. 同时构建默认和 opt-in 镜像，证明默认镜像未退化、opt-in 镜像能完成 CLI/适配器 smoke test。

### 阶段 E：评估、灰度与回滚

1. 准备 30-50 份受控语料：中文数字/扫描 PDF、合同、多栏论文、复杂表格、图片、公式、Tagged、空白页、长文档、加密/损坏 PDF、注入样本。
2. 对比 Docling、MinerU：完整页覆盖、阅读顺序、表格可用性、图片关联、注入处理、成功率、P50/P95、峰值内存。
3. 仅在独立 staging、独立 `WORKING_DIR`/KB 使用 `PDF_PARSER=opendataloader`；不要宣称按比例同集群灰度。
4. Go/No-Go 证据必须包括：测试报告、hash、镜像 digest、SBOM、notice/source hash、依赖对账、许可证批准、无部分入库、无安全回归、质量和资源结果。
5. 回滚方式：清除或恢复 `PDF_PARSER` 后重启 worker；新的 PDF 回到旧 parser，非 PDF 不受影响。已入库的新后端文档不会自动还原，必要时通过既有删除与重传流程重建。

## 10. 最终验收

完成后必须运行相关 parser、processor、worker、注入防护、上传任务测试，以及项目要求的 lint/format/type 检查；记录命令与结果。最终复核不得存在默认 parser 变化、optional 依赖泄漏、浮动版本、缺 notices、危险命令/路径、hybrid/远程参数、遗漏清理或 provenance 路径公开。

最后执行：

```text
openspec validate add-opendataloader-pdf-parser --strict
```

只有严格校验、真实页覆盖证明、供应链门禁和隔离灰度验收都通过后，才允许申请扩大使用范围。
