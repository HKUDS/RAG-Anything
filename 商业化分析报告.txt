1.2 致命缺陷清单（按严重程度排序）
无数据库持久化：知识库元数据存 JSON 文件，用户数据存 SQLite，无法支撑生产环境。
无部署方案：没有 Docker Compose / Kubernetes 部署配置，客户无法自行部署。
无 API 限流与安全防护：CORS 全开，无 Rate Limiting，单用户可耗尽所有资源。
无监控告警：没有 Prometheus/Grafana 集成，运维完全“盲飞行”。
无备份恢复机制：知识库数据仅存于本地文件系统，无自动备份、无灾难恢复方案。
无结构化日志：当前日志仅用 print/logging 输出到 stdout，无可检索的日志系统。
无审计日志：无法追踪“谁在什么时候做了什么”，无法满足企业客户合规要求。
无多租户隔离：知识库间无资源配额管理和数据隔离保障。
无性能基准：无压力测试、无并发测试数据，无法给客户 SLA 承诺。
无 License 管理：无法控制软件授权和到期，无法实现商业化收费。
前端功能缺失：文档生命周期管理不完整，缺乏预览、版本、批量操作等功能。

API Key 管理：每用户可生成多个 Key，每个 Key 可限定知识库范围、查询次数上限。
操作审计日志：记录所有敏感操作（登录/删除/配置变更），不可篡改。
2.2 文档生命周期管理
当前流程仅支持“上传→解析→查询”基础路径，缺乏完整的文档管理闭环。
文档状态面板：实时展示每个文档的处理阶段，WebSocket 推送进度更新。
文档预览：上传后预览解析结果（文本提取、图片 OCR、表格识别效果）。
批量操作：批量上传、删除、重新处理、导出（PDF/CSV/JSON）。
文档版本管理：同名文档重新上传后自动归档旧版本，支持版本回退。
标签与分类：自定义标签 + 文件夹组织，支持按标签筛选文档。
2.3 多模态能力增强
图片语义搜索：集成 CLIP 等视觉语义模型，支持“找一张包含架构图的图片”类自然语言检索。
视频理解：支持 MP4/MOV 等视频格式，自动提取关键帧并用 VLM 分析帧内容。
音频转录：支持 MP3/WAV 等音频格式，通过 Whisper 转录为文本后索引入库。
PDF 原生渲染：前端内嵌 PDF.js 查看器，支持页码跳转和搜索高亮。
2.4 分析与报表
使用仪表盘：文档数量趋势、查询量趋势、Token 消耗趋势（日/周/月）。
知识图谱可视化：D3.js 交互式实体关系图，支持节点展开/收起、搜索、导出。
成本分析面板：按模型、用户、知识库维度的费用统计。
用户行为分析：最常查询的关键词、高频问题云图、查询失败率监控。
2.5 企业级必需功能
SSO 单点登录：支持 OAuth2 / OIDC / SAML 协议，对接企业统一身份认证。
LDAP/AD 集成：企业内部目录服务对接，自动同步组织架构和用户。
Webhook 事件通知：文档处理完成、知识库更新、异常告警等事件自动推送。
数据导出：知识库内容导出为 PDF/CSV/JSON，支持全量或选择性导出。
白标 (White Label)：自定义 Logo、品牌配色、域名。企业客户强需求。
国际化 (i18n)：中英文界面切换，为海外市场做准备。
2.6 用户引导与首次使用体验 [v2.0 新增]
当前问题：用户注册后面对空知识库界面，没有任何引导。“我该先做什么？”是用户的第一个困惑。
首次使用向导 (Onboarding Wizard)：3 步引导——上传第一份文档 → 等待处理 → 发起第一次查询。每步带可视化提示。
示例知识库：提供“一键导入示例文档”功能，新用户立即能体验查询效果。
空状态设计：知识库为空时显示友好的“开始上传”入口，而非白屏。
帮助中心：内置常见问题 + 视频教程链接，降低支持成本。
2.7 知识库协作功能 [v2.0 新增]
企业场景下，多人协作维护知识库是刚需。
共享链接：生成可共享的知识库查询链接，支持权限控制和过期时间。
评论与 @提及：在查询结果中评论特定内容，@提及团队成员协作完善知识库。
知识库模板：预定义知识库结构模板（如“产品手册”“客服 FAQ”），一键创建。
2.8 搜索体验细节 [v2.0 新增]
搜索结果高亮：查询关键词在回答中高亮显示，帮助用户快速定位目标内容。
相关搜索推荐：“您可能还想问…”——基于其他用户的查询模式推荐相关问题。
搜索範围筛选器：按文档、日期范围、内容类型（图片/表格/文本）筛选。
搜索历史：保存并展示用户搜索历史，支持重新执行和收藏。
2.9 错误处理与用户反馈 [v2.0 新增]
处理失败重试：文档处理失败后提供“重试”按钮，显示具体错误原因和解决建议。
用户反馈入口：每个查询结果旁提供“赞/踩”按钮，用于改善检索质量。
错误日志可见性：用户可查看文档处理的详细日志，了解失败原因。
响应式布局：前端至少支持桌面和平板的响应式布局。

改进措施：
引入任务队列 (Celery/Redis Queue)：文档解析和实体提取异步化，前端通过 WebSocket 获取实时进度。
LLM 连接池：实现 HTTP 连接复用，避免每次请求重新建立 TCP 连接。
Redis 缓存层：相同查询结果缓存（可配置 TTL），重复查询直接返回，降低 LLM API 成本。
3.2 向量检索性能
当前使用 LightRAG 内置向量存储（基于 NumPy/Pickle），适合原型和小规模场景，但面对 100 万+ chunk 时性能急剧下降。
迁移到专业向量数据库：Milvus（高性能 C++ 实现）/ Qdrant（Rust 实现）/ Weaviate（内置向量+对象存储）。
向量索引分片：按知识库或文档粒度分片，避免全量扫描。
热/冷数据分层：频繁访问的知识库加载到内存，低频数据存磁盘。
3.3 大文件处理
流式文档解析：当前 Docling/MinerU 全量加载文档到内存。需要改造为流式处理，降低内存峰值。
分块处理 + 断点续传：超大文档（500MB+）分批处理，失败后可从中断点恢复。
内存上限控制：为解析进程设置内存限制，超限时自动降级。
3.4 资源评估基准
单文档处理基准：按文件类型和大小记录处理耗时。
并发查询 QPS-延迟曲线：在不同并发量下测量 P50/P95/P99 延迟。
硬件推荐配置：小中大规模的推荐 CPU/内存/GPU/存储配置。

4.2 数据安全
传输加密：强制 HTTPS/TLS 1.3，HTTP 自动重定向到 HTTPS。
存储加密：知识库向量数据 AES-256-GCM 加密存储。
API Key 保护：创建时返回完整 Key，之后仅存储 bcrypt 哈希。
敏感信息脱敏：日志中自动脱敏 API Key、密码、Token、邮箱等敏感字段。
4.3 API 安全
Rate Limiting：按用户/IP/API Key 三级限流。默认 100 请求/分钟/用户，可配置。
请求大小限制：上传文件最大 500MB，请求 Body 最大 10MB。
CORS 白名单：替换当前的 allow_origins=["*"]，仅允许配置的域名列表。
安全响应头：添加 CSP、X-Content-Type-Options、X-Frame-Options、Strict-Transport-Security 等。
输入校验：Prompt Injection 防护、SQL 注入防护、XSS 过滤。
4.4 合规与隐私
GDPR 合规：用户数据导出权、删除权，数据处理协议模板。
《个人信息保护法》合规：数据本地化存储、个人信息保护影响评估 (PIA) 流程。
SOC 2 Type II：12-18 个月认证路径。
数据本地化：支持指定数据存储区域。
4.5 运维安全
CI/CD 安全：GitHub Actions 集成 SAST（CodeQL/Semgrep）和依赖扫描（Dependabot/Snyk）。
Docker 镜像安全：基础镜像使用 distroless/alpine-slim，定期 CVE 扫描。
密钥管理：生产环境禁止 .env 文件，使用环境变量 + Secrets Manager/Vault。
4.6 威胁建模 (Threat Model) [v2.0 新增]
当前报告列了安全需求但没做 STRIDE 威胁建模——攻击面在哪里？最高风险路径是什么？
主要攻击面：API 接口（未授权访问/注入）、文档解析引擎（恶意文档）、LLM 调用（Prompt Injection）、向量数据库（数据泄露）。
建议做法：每个重大功能发布前执行 STRIDE/Linddun 威胁建模，输出威胁模型文档。
4.7 数据分类与分级 [v2.0 新增]
客户上传的文档可能含商业机密/PII/PHI，需要自动分类和分级处理策略。
数据分级标准：公开级/内部级/机密级/绝密级，不同级别对应不同存储和访问策略。
4.8 供应链安全 [v2.0 新增]
项目依赖 100+ PyPI 包 + LightRAG + Docling + MinerU，攻击面分析和 SBOM（软件物料清单）必不可少。
定期执行 pip-audit / safety 扫描，依赖更新策略。
4.9 安全响应 SLA [v2.0 新增]
漏洞发现→修复→通知客户的流程和时间承诺，客户合同里必须写：
批判级漏洞 (CVSS >= 9.0)：24 小时内修复 + 紧急通知客户。
高危漏洞 (CVSS 7.0-8.9)：72 小时内修复。
中危漏洞 (CVSS 4.0-6.9)：下个版本迭代修复。
4.10 渗透测试计划 [v2.0 新增]
商业化前至少需要一次第三方渗透测试报告。
建议测试范围：Web 应用渗透测试 (OWASP Top 10)、API 安全测试、LLM 安全测试 (OWASP LLM Top 10)。

5.2 服务拆分路线图
Phase 1 (1-3月)：模块化重构。将 server.py 拆分为独立的 service 模块，仍运行在同一进程内。
Phase 2 (4-6月)：独立服务。Auth Service + API Gateway + Query Service + Parser Worker。
Phase 3 (7-12月)：完整微服务化。引入消息队列 (RabbitMQ/Kafka) 解耦服务间同步依赖。
5.3 部署方案（最紧急）
Docker 单机部署（docker-compose.yml）：app + PostgreSQL + Redis + Nginx 四容器编排，docker compose up 一键启动。
K8s 集群部署（Helm Chart）：包含 HPA、Ingress、ConfigMap、Secret 管理等。
环境变量管理：提供 .env.example 模板，所有配置项有注释说明。
健康检查端点：/api/health（返回 200 + 各组件连接状态）。
5.4 可观测性
OpenTelemetry：全链路追踪，覆盖 HTTP 请求 → Service 层 → LLM API 调用 → 返回。
结构化日志：JSON 格式输出，包含 trace_id/user_id/kb_id 等上下文字段。
Prometheus Metrics：请求量、延迟、错误率、资源使用等关键指标。
Grafana 仪表盘：预置 3 套模板（概览/性能/业务）。
告警通道：PagerDuty / Slack / 企业微信 / 钉钉 Webhook。
5.5 API 版本化策略 [v2.0 新增]
REST API 作为产品接口，必须有版本管理和废弃策略：
URL 路径版本化：/api/v1/query、/api/v2/query。
废弃策略：旧版本支持至少 6 个月，废弃前 3 个月通过 HTTP 响应头 Deprecation 通知。
版本变更日志：CHANGELOG.md 维护每个版本的破坏性变更、新功能、废弃。
5.6 数据迁移工具 [v2.0 新增]
JSON→PostgreSQL 迁移脚本：一键迁移知识库元数据、查询历史、用户数据。
升级指南：从旧版本升级到新版本的分步骤文档，包含备份、迁移、验证三步。
5.7 高可用架构 [v2.0 新增]
报告没提 HA——数据库主从、服务多副本、负载均衡。企业客户要 99.9% SLA。
PostgreSQL 主从复制（Streaming Replication），自动故障切换。
服务多副本 + Nginx/Traefik 负载均衡，单节点故障不影响服务可用性。
目标 SLA：99.9% 可用性（每月允许 43.8 分钟宕机时间）。
5.8 灾备方案细节 [v2.0 新增]
RPO（数据丢失窗口）：< 5 分钟（实时主从复制）。
RTO（服务恢复时间）：< 30 分钟（自动故障切换 + 预热备份）。
异地灾备：支持异地备份到 S3/对象存储，每季度灾备演练。
5.9 插件/扩展架构 [v2.0 新增]
通过插件机制让第三方贡献解析器/模型/UI 组件——这是 Dify 的核心竞争力之一。
插件类型：文档解析器插件、LLM 模型插件、向量数据库插件、UI 主题插件。
插件市场：官方插件商店，开发者可上架付费插件，平台抽成 30%。

6.4 销售渠道
开源社区转化：GitHub Stars → 文档站 → 免费试用 → 付费转化。目标转化率 2-5%。
内容营销：技术博客、B站教学视频、知乎技术文章。
云市场入驻：阿里云计算巢/腾讯云应用商店/AWS Marketplace。
系统集成商合作：与 OA/ERP 厂商合作，成为其文档 AI 模块供应商。

6.6 市场规模 TAM/SAM/SOM [v2.0 新增]
TAM（总可达市场）：中国企业知识管理软件市场 ~120 亿 RMB（IDC 2025）。
SAM（可服务市场）：AI 文档分析细分市场 ~15-20 亿 RMB（可通过内容营销触达的部分）。
SOM（可获得市场）：年收入目标 ¥500 万（第一年）→ ¥3,000 万（第三年）。
6.7 竞争护城河深度分析 [v2.0 新增]
“多模态”是护城河，但能持续多久？
AnythingLLM 加个 VLM 插件需要多久追上？估计 3-6 个月。需要在这之前建立数据飞轮和品牌壁垒。
数据护城河：客户的知识库数据就是最大的转换成本——一旦建好就不会轻易迁移。
生态护城河：通过插件市场 + API 开放，让第三方开发者为你的平台贡献价值。
6.8 海外市场策略 [v2.0 新增]
报告以国内市场为主，但海外企业文档 RAG 市场更大：
海外竞品：Glean（企业搜索，估值 $2.2B）、Nuclia（多模态 RAG API）、LlamaIndex（开源框架）。
进入策略：先发英文版文档 + GitHub 英文 README，通过 Hacker News / Product Hunt 获取海外早期用户。
6.9 退出策略 [v2.0 新增]
被收购是最现实的退出路径——潜在收购方：企业 OA/ERP 厂商、云厂商、AI 平台公司。
持续经营也可行：年经营收入¥1,000-3,000 万可维持 5-10 人团队。
七、实施路线图
Phase 1：MVP 加固 (第 1-2 月)
Docker 一键部署 (docker-compose.yml：app + PostgreSQL + Redis + Nginx)
PostgreSQL 替代 JSON/SQLite（用户/权限/元数据/查询历史迁移）
API Rate Limiting + CORS 白名单 + 安全响应头
结构化日志（JSON 格式，日志轮转）
前端：文档状态面板 + 批量操作 + 实时进度条 + 首次使用向导
基础监控 (Prometheus + Grafana 预置仪表盘)
Phase 2：商业可用 (第 3-4 月)
License 管理 (激活码/到期提醒/功能开关)
多租户 + RBAC 权限 (5 级角色)
Redis 缓存层 (查询缓存 + Session 存储)
自动备份 + 一键恢复
Webhook 事件通知
使用分析仪表盘 + 成本分析面板
定价页面 + 支付集成 (微信支付/支付宝)
Phase 3：企业级 (第 5-6 月)
SSO / OAuth2 / LDAP 集成
向量数据库迁移 (Milvus/Qdrant，支持 GPU 加速)
审计日志 (不可篡改的合规审计)
白标定制 (自定义 Logo/域名/配色)
K8s Helm Chart + 弹性伸缩
性能压测报告 (含 QPS-延迟曲线和硬件配置建议)
安全合规文档 (SOC 2 准备/等保差距分析) + 第三方渗透测试
Phase 4：规模化 (第 7-12 月)
微服务拆分 (Auth/Parser/Query/Gateway 独立部署和扩缩容)
多语言 i18n (中/英/日)
视频 + 音频多模态处理
Marketplace 插件生态 (解析器/模型/UI 主题插件)
云托管 SaaS 版本 (免部署，按量计费)

8.2 最优先做的 3 件事
① Docker 化部署 — 让客户 5 分钟跑起来。没有这一步，其他一切改进都无法触达客户。
② PostgreSQL 数据库迁移 — 这是所有企业功能（多租户/RBAC/审计/备份）的基础。
③ API 安全加固 — Rate Limiting + 输入校验 + CORS 白名单。不加固，不敢让客户把系统暴露到公网。
